# 0016. Delimiter Layering — لایه‌بندی نویسه‌های محصورکننده

**Status:** Accepted
**Date:** 2026-10-16
**Deciders:** حسین س، دی

## Context

در کارهای روزمره‌ی این پروژه، سه لایه‌ی متفاوت از «محصورکردن متن» با هم قاطی می‌شن:

۱. **لایه‌ی چت** — وقتی AI کدی رو برای کاربر نمایش می‌ده، از سه‌بک‌تیک (` ``` `) استفاده می‌کنه.
۲. **لایه‌ی فایل markdown** — وقتی AI محتوای یه ADR یا سند رو داخل heredoc می‌نویسه، همون متن markdownـه که خودش می‌تونه هدر (`#`) و بلاک کد (` ``` `) داشته باشه.
۳. **لایه‌ی terminal** — heredoc با delimiter، که نویسه‌های خاصی مثل backtick، `#`، `$` رو در shell تفسیر می‌کنه.

### مشکل واقعی

امروز (2026-10-16) در نوشتن `docs/adr/0015-user-paper-state.md`، دو بار به مشکل خوردیم:

**الف) گره‌خوردن ` ``` ` توی ` ``` `** — وقتی می‌خواستیم داخل ADR (که خودش markdownـه) یه بلاک Python بذاریم، سه‌بک‌تیک داخلی با بیرونی گره خورد. markdown فکر کرد بلاک کد تموم شده، متن بعدی رو به‌عنوان متن آزاد تفسیر کرد.

**ب) `backtick` در shell** — توی heredoc بدون تک‌کوتیشن، backtick = command substitution. حتی با `'MY_EOF'` (تک‌کوتیشن) امن می‌شه، ولی همچنان مشکل گره‌خوردن باقیه.

**ج) M19 در جدول markdown** — وقتی خواستیم سه‌بک‌تیک رو در سلول جدول بنویسیم (`| M19 | ... ``` ... |`)، markdown جدول رو شکست — چون سه‌بک‌تیک شروع بلاک کد رو اعلام می‌کنه.

### قاعده‌ی فعلی (ناقص)

`AI_PRIMER.md` فقط می‌گه «markdown را در ترمینال paste نکن» و «از heredoc استفاده کن». ولی **نگفته** که:
- اگه خودِ محتوا markdown باشه چی؟
- اگه بخوایم بلاک کد تودرتو داشته باشیم چی؟
- اگه بخوایم نویسه‌ی محصورکننده رو در جدول بنویسیم چی؟

## Decision

**قاعده‌ی سه‌لایه:**

| لایه | نویسه | کاربرد |
|------|-------|--------|
| بیرونی (چت) | سه‌بک‌تیک | نمایش کد به کاربر |
| میانی (markdown) | سه‌هش (`#`, `##`, `###`) | هدر و تیتر |
| داخلی (markdown تودرتو) | سه‌تیلد (`~~~`) | بلاک کد داخل سند |
| inline در جدول/متن | توصیف متنی | «سه‌بک‌تیک» به‌جای خود نویسه |

### قواعد عملی

**۱. بیرونی = سه‌بک‌تیک.** همه‌ی بلاک‌های کد که در چت به کاربر نشون داده می‌شن، با سه‌بک‌تیک باز و بسته می‌شن.

**۲. هدر در markdown = سه‌هش.** برای تیترها در سند markdown، از `#`، `##`، `###` استفاده می‌کنیم. چون `#` در shell کامنته، این نویسه در heredoc هم امنه.

**۳. بلاک کد تودرتو در markdown = سه‌تیلد.** وقتی سند markdown خودش می‌خواد یه بلاک کد داشته باشه، از `~~~` استفاده می‌کنیم (نه سه‌بک‌تیک). markdown سه‌تیلد رو معادل سه‌بک‌تیک می‌دونه، ولی با سه‌بک‌تیک بیرونی گره نمی‌خوره.

**۴. نویسه‌ی محصورکننده در جدول = توصیف متنی.** وقتی می‌خوایم خود نویسه رو در جدول یا پاراگراف بنویسیم، از توصیف متنی استفاده می‌کنیم:
- «سه‌بک‌تیک» به‌جای ` ``` `
- «سه‌هش» به‌جای `###`
- «سه‌تیلد» به‌جای `~~~`

**۵. delimiter heredoc = یکتا + تک‌کوتیشن.** هر heredoc باید delimiter یکتا داشته باشه (`'ADR_0016_EOF'`، نه `'EOF'`) و با تک‌کوتیشن محصور بشه تا shell نویسه‌های داخلی رو تفسیر نکنه.

### مثال درست

ساخت یه ADR با بلاک Python تودرتو:

~~~bash
cat > docs/adr/0017-example.md << 'ADR_0017_EOF'
# 0017. عنوان

## Context

متن توضیحی.

### نمونه کد

~~~python
def foo() -> int:
    return 42
~~~

## Decision

...
ADR_0017_EOF
~~~

نکته: بلاک بیرونی سه‌بک‌تیک (چت)، محتوای heredoc شامل سه‌هش (هدر) و سه‌تیلد (بلاک Python تودرتو).

### مثال غلط

استفاده از سه‌بک‌تیک تودرتو:

~~~bash
cat > docs/adr/0017-example.md << 'ADR_0017_EOF'
# 0017. عنوان

### نمونه کد

(اینجا سه‌بک‌تیک، نه سه‌تیلد)
def foo() -> int:
    return 42
(اینجا بستن سه‌بک‌تیک)

## Decision
...
ADR_0017_EOF
~~~

در این مثال، سه‌بک‌تیک داخلی با سه‌بک‌تیکِ بسته‌ی بلاک بیرونی گره می‌خوره، heredoc ناقص می‌مونه، و خطوط بعدی به‌عنوان دستور shell اجرا می‌شن.

### چک‌لیست قبل از ارسال

- [ ] بلاک بیرونی با سه‌بک‌تیک شروع و تموم شده؟
- [ ] داخل markdown از سه‌هش برای هدر استفاده شده؟
- [ ] اگه بلاک کد تودرتو لازم بود، از سه‌تیلد استفاده شد؟
- [ ] اگه نویسه‌ی محصورکننده در جدول/متن میاد، توصیف متنی به‌کار رفته؟
- [ ] delimiter heredoc یکتاست؟
- [ ] delimiter با تک‌کوتیشن محصور شده؟

## Consequences

- **Positive:**
  - سه لایه از هم جدا می‌مونن، گره نمی‌خورن.
  - سند markdown سالم می‌مونه، heredoc ناقص نمی‌شه.
  - قاعده‌ی روشن برای AI بعدی — نیازی به کشف دوباره نیست.

- **Negative:**
  - سه‌تیلد در برخی rendererهای قدیمی markdown پشتیبانی نمی‌شه (نادر — GitHub، GitLab، VS Code همه پشتیبانی می‌کنن).
  - AI جدید باید این قاعده رو یاد بگیره (ولی با M19 در AI_PRIMER، سریع یاد می‌گیره).

- **Neutral:**
  - جایگزین‌های دیگه (نویسه‌ی یونیکد، HTML `<pre>`) بررسی شدن ولی پیچیده‌ترن و portability کمتری دارن.
